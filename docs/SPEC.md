## 0. Как работать с этим файлом

Ты AI-агент, который с нуля собирает рабочий веб-MVP с поддержкой PWA. Этот файл единственный источник требований. Положи его в репозиторий как `docs/SPEC.md`, а в корне создай `AGENTS.md` и `CLAUDE.md` с одной строкой: «Все требования в docs/SPEC.md, работай по разделу 3».

### Правила работы

1. Работай по этапам из раздела 3 строго по порядку. Этап закрыт, только когда проходят все его проверки.
2. Все предметные данные (вопросы, услуги, документы, поставщики, источники, правила) бери только из разделов 5–10. Не придумывай услуги, сроки, документы, нормативные акты, адреса и телефоны.
3. Если данных не хватает, ставь в коде или JSON метку `TODO(mentor)` и добавляй строку в `docs/OPEN_QUESTIONS.md`. Не заполняй пробел догадкой.
4. Продукт не ставит диагнозы. Это касается кода, текстов интерфейса, промптов, тестовых данных и комментариев.
5. План строит только движок правил, и это чистая функция. LLM никогда не выбирает услуги, сроки, приоритеты и статусы.
6. Решение, которого нет в спецификации, записывай в `docs/DECISIONS.md` одной строкой с причиной.
7. После каждого этапа обнови `docs/PROGRESS.md` (что сделано, как проверить руками), прогони тесты и сделай коммит с префиксом этапа, например `stage-1: engine`.
8. Секреты только через `.env`. В репозитории лежит `.env.example` с пустыми значениями.
9. Тексты интерфейса никогда не пиши в компонентах напрямую, только через файлы переводов `ru` и `kk`.

## 1. Продукт

Родители детей с РАС теряются между медициной, образованием и соцзащитой, повторно собирают документы, а специалисты не видят полного маршрута ребёнка, из-за чего помощь затягивается. AqylRoute решает это так: родитель проходит AI-интервью из 8–12 адаптивных вопросов, движок правил по справочнику реальных услуг строит межведомственный Case Plan, куратор проверяет и подтверждает его, после чего сервис ведёт статусы, контролирует сроки и эскалирует просрочки.

Четыре принципа, которые нельзя нарушать:

1. **AI понимает, код решает.** LLM выбирает следующий вопрос из банка, разбирает свободный текст и документы, пишет объяснения. Состав плана, порядок и сроки определяет движок.
2. **Только справочник.** Каждый шаг плана это услуга из `data/services.json`. Шаг вне справочника создать невозможно ни через AI, ни через API.
3. **Без диагнозов.** Интервью спрашивает, что уже сделано и что есть на руках. Все тексты LLM проходят фильтр формулировок.
4. **Человек подтверждает.** Родитель видит план только после подтверждения куратором. Любое изменение создаёт новую версию.

## 2. Стек и структура репозитория

Стек задан кейсом: Next.js, FastAPI, OpenAI structured outputs, SQLite или Supabase.

| Слой | Технологии |

## 3. Этапы работы

### Этап 0. Систематизация данных

Перенеси разделы 5–10 в JSON-файлы папки `data/` и напиши к ним JSON Schema.

- `questions.json`: 18 вопросов из раздела 5, каждый с полями `id`, `text_ru`, `text_kk`, `answer_type`, `options[]` (`code`, `label_ru`, `label_kk`), `show_if`, `profile_field`, `priority`, `mandatory`, `order`, `source_ids[]`, `needs_review`.
- `services.json`: 15 услуг из раздела 6.
- `document_types.json`, `providers.json`, `sources.json`: разделы 8 и 9.
- Казахские тексты переводишь сам и ставишь `needs_review: true`, их проверит носитель языка.

**Проверки этапа (pytest `tests/test_data.py`):**

- каждый файл проходит свою JSON Schema;
- все ID в `show_if` существуют в `questions.json`, все коды вариантов в `show_if` существуют у соответствующего вопроса;
- каждый `profile_field` вопроса есть в схеме профиля из раздела 10;
- все `predecessors_any` и документы услуг ссылаются на существующие `service_id` и `doc_type`;
- у каждой услуги либо есть `source_ids`, либо `sla_verified: false`;
- в `questions.json` ровно 6 вопросов с `mandatory: true`.

### Этап 1. Ядро API

Модели и миграции (раздел 14), авторизация и роли, модуль интервью (раздел 11.1), движок правил (раздел 11.2), модуль планов со статусами и версиями (разделы 10, 11.4).

**Проверки:** автотесты по фикстурам из раздела 19 дают ровно ожидаемые планы; повторный прогон даёт побайтно одинаковый `steps`; попытка добавить шаг с несуществующим `service_id` возвращает 422; родитель не может получить план в статусе `draft` и чужую семью.

### Этап 2. Сроки, эскалация, документы, уведомления, PDF

Планировщик и эскалация (раздел 11.3), кошелёк документов и распознавание (раздел 8), LLM-модуль (раздел 12), уведомления (раздел 18), PDF (раздел 17), эндпоинт сдвига времени для демо.

**Проверки:** сценарии сдвига времени из раздела 19 дают ожидаемые уровни эскалации и сроки; загрузка тестового PDF заключения ПМПК обновляет `pmpk.valid_until`; все три PDF-отчёта генерируются на обоих языках.

### Этап 3. Web: родитель и куратор

Все экраны из раздела 15 на двух языках, дизайн по разделу 15.3.

**Проверки:** оба синтетических кейса проходятся руками от интервью до эскалации уровня 3 без обращения к API напрямую.

### Этап 4. PWA

Всё из раздела 16.

**Проверки:** из раздела 16.6.

### Этап 5. Демо и деплой

Сид демо-аккаунтов и кейсов, деплой по публичной ссылке, прохождение чек-листа приёмки из раздела 20.

## 4. Глоссарий

| Термин | Значение |
| --- | --- |
| РАС | Расстройство аутистического спектра. В продукте упоминается только в названиях услуг и описании сервиса, никогда в утверждениях о конкретном ребёнке |
| ПМПК | Психолого-медико-педагогическая консультация. Обследует ребёнка и выдаёт заключение об условиях обучения. Диагнозов не ставит |
| Заключение ПМПК | Документ с рекомендациями: тип программы, форма обучения, педагог-ассистент, кабинеты коррекции, реабилитация. Действует до даты, указанной в самом заключении |
| КППК | Кабинет психолого-педагогической коррекции |
| Педагог-ассистент | Сопровождающий ребёнка в саду или школе по рекомендации ПМПК, в разговорной речи тьютор |
| МСЭ | Медико-социальная экспертиза, устанавливает инвалидность |
| ИПР | Индивидуальная программа реабилитации, выдаётся по итогам МСЭ |
| ВКК | Врачебно-консультационная комиссия, в том числе выдаёт заключение о необходимости обучения на дому |
| Куратор | Специалист, который ведёт семьи, подтверждает планы, ведёт статусы и реагирует на просрочки |
| Case Plan | План семьи: версия, статус, список шагов. Хранится одной JSON-структурой |
| Шаг | Одна услуга из справочника в плане семьи с приоритетом, ответственным, сроком, документами и статусом |

## 5. Банк вопросов

Банк из 18 вопросов. Каждое условие в справочнике услуг проверяется одним вопросом, документы и сроки взяты из правил госуслуги ПМПК (источник `SRC_ADILET_223`). Вопросы не оценивают признаки РАС.

### 5.1. Формат `show_if`

Условие записывается JSON-объектом. Допустимые операторы: `always`, `eq`, `in`, `gte`, `lt`, `contains`, `not_contains`, `any` (или), `all` (и). Пример:

```json
{ "any": [ { "q": "Q03", "op": "eq", "value": "home" }, { "q": "Q02", "op": "eq", "value": "yes" } ] }
```

Вопрос, на который ещё не ответили, делает условие ложным.

`filler` означает: вопрос допустим всегда, но задаётся только если без него интервью не набирает 8 ответов или LLM выбрал его при свободном лимите.

У вариантов `none` в множественном выборе включена взаимоисключаемость: выбор `none` снимает остальные.

### 5.3. Подсказки к вопросам

У каждого вопроса есть поле `hint_ru` и `hint_kk`: одна строка «зачем мы спрашиваем». Напиши их сам по смыслу поля профиля, например для Q14: «Отмеченные документы не придётся собирать заново, мы подставим их в нужные шаги». Подсказки не должны содержать медицинских утверждений.

### 5.4. Чего в банке нет намеренно

- Диагноза и предварительного диагноза, хотя они есть в журнале ПМПК.
- Медицинской карты формы 052/у и психолого-педагогической характеристики как вопросов к родителю: их ПМПК запрашивает сама.
- ФИО и ИИН ребёнка: они вводятся в карточке семьи и никогда не уходят в LLM.
- Любых вопросов из скрининговых инструментов аутизма (M-CHAT, ADOS, ADI-R, CARS и подобных).

По источнику `SRC_ADILET_223`: ожидание в очереди на обследование до 30 календарных дней; при личном обращении дата назначается в день обращения, через портал в течение 2 рабочих дней; заключение выдаётся в день обследования или приходит в личный кабинет в течение 2 рабочих дней. Для плана берётся 30 дней очереди плюс 2 дня на заключение.

### 6.4. Срок действия заключения ПМПК

Срок указывается в каждом заключении отдельно (поле «Заключение действительно до»), поэтому движок берёт его из профиля (`pmpk.valid_until`) или из загруженного заключения. В расчётах эти ориентиры не используются.

## 11. Алгоритмы

### 11.1. Интервью

Состояние интервью хранится в таблице `interviews`: `answers` это массив `{question_id, value, answered_at}` в порядке ответов.

Один шаг `POST /interview/answer`:

1. Сохранить ответ, провалидировать его по типу и вариантам вопроса. Для `multi` с вариантом `none` оставить только `none`.
2. Вычислить `allowed`: вопросы без ответа, у которых `show_if` истинно на текущих ответах. `filler` допустимы всегда.
3. Если ответов 12, интервью закрывается, вернуть `{done: true}`.
4. Если среди `allowed` есть обязательные, следующий вопрос это первый из них в фиксированном порядке (Q01, Q02, Q03, Q04, Q14, Q16). LLM не вызывается.
5. Иначе, если в `allowed` нет вопросов кроме `filler` и ответов уже не меньше 8, интервью закрывается.
6. Иначе вызвать LLM (раздел 12, вызов 1) со списком `allowed`. Если ответ невалиден или LLM недоступен, взять первый вопрос из `allowed` по приоритету, затем по номеру.
7. Если ответов меньше 8 и `allowed` пуст, добавить Q17, затем Q18.

`POST /interview/back` удаляет последний ответ и пересчитывает состояние. `POST /interview/finish` доступен при 8 и более ответах: строит профиль, вызывает LLM для Q17 (вызов 2), затем движок, затем объяснения, и сохраняет план со статусом `draft`.

**Профиль** собирается кодом по `profile_field`. `unknown_fields` это поля вопросов, которые были допустимы в момент закрытия интервью, но не были заданы. Флаги из Q17 добавляются в `red_flags` с пометкой источника `from_text` и показываются куратору отдельно.

**«Уточнить у семьи»:** куратор выбирает вопрос из `unknown_fields`, родитель видит его в кабинете, ответ обновляет профиль, движок пересчитывает черновик. Если план уже подтверждён, создаётся новая версия `draft`, которую куратор снова подтверждает.

### 11.2. Движок

`build_plan(profile, catalog, computed_at) -> steps` это чистая функция без обращений к БД, сети и LLM.

1. Выполнить правила R01–R14 по порядку. Если одна услуга добавлена несколькими правилами, оставить самый высокий приоритет и первый `rule_id`.
2. Для каждой услуги `depends_on` это все услуги из её `predecessors_any`, которые есть в плане.
3. Обойти граф в топологическом порядке и посчитать даты:
    - `start_date` = максимум из `computed_at` и `deadline` всех зависимостей;
    - для `sla.type = days`: `deadline = start_date + value`;
    - для `sla.type = before_field`: `deadline = field_date − days`. Если поле пустое, использовать `start_date + min_days` и поставить `needs_clarification: true`;
    - если `deadline < start_date + min_days`, взять `start_date + min_days`, поставить `priority: critical` и `deadline_compressed: true`. `min_days` у EDU_PMPK_RENEW 32, у SOC_DISABILITY_REVIEW 30.
4. `status` = `blocked`, если есть зависимости, иначе `not_started`.
5. Документы шага собрать из `documents.*` услуги. `in_wallet` = документ есть в кошельке с непросроченным сроком или отмечен в `docs.present`. Применить R15.
6. Отсортировать по рангу приоритета (critical, high, medium, low), затем по `deadline`, затем по `service_id`. Пронумеровать S1…Sn и заменить `depends_on` на `step_id`.
7. Проверить: все `service_id` в справочнике, граф без циклов, у каждого шага заполнены `priority`, `responsible`, `deadline`, `documents`, `status`. При ошибке бросить исключение с `rule_id` и описанием.

Все даты календарные, часовой пояс `Asia/Almaty`, формат ISO `YYYY-MM-DD`.

Объяснения к шагам не часть движка. Их добавляет модуль LLM после построения по ключу `service_id + возрастная группа + язык` (группы `0-2`, `3-6`, `7-17`).

### 11.3. Сроки и эскалация

Текущая дата берётся только через сервис часов `clock.today()`, который учитывает сдвиг из `settings.time_offset_days` (демо). Прямые вызовы `date.today()` запрещены.

Планировщик запускается раз в час и при каждом `GET /plans/{family}`:

1. Для шагов в статусах `not_started`, `in_progress`, `blocked`: `overdue_days = today − deadline`.
2. Если `overdue_days ≥ 1`, статус `overdue`. Шаги `done_by_parent` и `done` не просрочиваются.
3. Уровень эскалации:

| Уровень | Условие | Действие | Кому |
| --- | --- | --- | --- |
| 0 | `deadline − today ≤ 3` и шаг не выполнен | Напоминание | Ответственному. Если это `education_org`, то куратору |
| 1 | `overdue_days ≥ 1` | Статус `overdue`, пересчёт зависимых | Родителю и куратору |
| 2 | `overdue_days ≥ 7` | Шаг в блоке «Требует действия» | Куратору |
| 3 | `overdue_days ≥ 14` | Метка «эскалировано в ведомство», генерируется текст обращения | Куратору |

Каждый уровень срабатывает один раз на шаг и пишется в `escalations`.

4. Пересчёт зависимых: для невыполненного просроченного шага ожидаемая дата завершения = `today`. Сроки зависимых шагов пересчитываются по правилам 11.2 (пункт 3), `original_deadline` не меняется.
5. Текст обращения уровня 3 собирается по шаблону: ведомство, услуга, дата обращения семьи, регламентный срок со ссылкой на источник, число дней просрочки. LLM не используется.

**Версии.** Новая версия плана создаётся при построении черновика, при правке куратором и при подтверждении. Смена статусов и пересчёт сроков планировщиком меняют текущую версию на месте, пишутся в `status_history` шага и в `audit_log`. Запиши это решение в `docs/DECISIONS.md`.

### 11.4. Переходы статусов шага

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| `blocked` | `not_started` | система | все шаги из `depends_on` в `done` |
| `not_started` | `in_progress` | родитель или куратор | работа начата |
| `not_started`, `in_progress`, `overdue` | `done_by_parent` | родитель | кнопка «Я сделал» на шаге с `responsible = parent` |
| `done_by_parent` | `done` | куратор | подтверждение |
| `done_by_parent` | `in_progress` | куратор | отклонение с комментарием |
| `not_started`, `in_progress`, `blocked` | `overdue` | система | срок прошёл |
| `overdue` | `in_progress` | куратор | перенос срока с обязательной причиной |
| любой, кроме `done` | `done` | куратор | ручное закрытие с комментарием |

Любой другой переход API отклоняет с кодом 409.

## 12. LLM-модуль

Все вызовы через один модуль `modules/llm/`. Настройки: модель из `OPENAI_MODEL` (любая с поддержкой structured outputs в режиме `json_schema` со `strict: true`), `temperature: 0`, `seed: 42`. Ответы кешируются в таблице `llm_cache` по SHA-256 от типа вызова и входа. Если `OPENAI_API_KEY` пуст, модуль работает в режиме заглушки: вызов 1 возвращает первый допустимый вопрос, вызов 2 пустой результат, вызов 3 шаблон из справочника, вызов 4 пустые поля. Тесты всегда используют заглушку или мок.

### 12.1. Маскирование

Перед каждым вызовом: имя ребёнка, ФИО родителей, 12-значные числа (ИИН), телефоны, email и точные адреса заменяются метками `[CHILD]`, `[PARENT]`, `[ID]`, `[PHONE]`, `[EMAIL]`, `[ADDRESS]`. Обратная подстановка не нужна, в ответах LLM этих данных быть не должно.

### 12.2. Вызовы

**Вызов 1. Выбор следующего вопроса.**

Вход: ответы (ID, короткий текст вопроса, значение), список `allowed` с приоритетами. Схема ответа: `{ "next_question_id": enum(allowed) }`.

Системный промпт:

```
Ты модуль интервью сервиса, который помогает семье пройти маршрут помощи ребёнку между медициной, образованием и соцзащитой. Выбери следующий вопрос только из списка allowed. Сначала вопросы с приоритетом high, затем medium, затем low. Среди равных выбери тот, ответ на который сильнее всего меняет маршрут семьи с учётом уже данных ответов. Не выбирай Q17 и Q18, если в allowed есть другие вопросы. Ты не оцениваешь состояние ребёнка и не делаешь выводов о здоровье. Верни только JSON по схеме.
```

**Вызов 2. Разбор ответа Q17.**

Вход: текст ответа после маскирования. Схема: `{ "red_flags": enum[] из [regression, seizures, danger], "priority_focus": enum из кодов Q18 или null }`.

```
Ты извлекаешь из текста родителя только явно названные ситуации из закрытого списка: regression (ребёнок перестал делать то, что уже умел), seizures (судороги или потеря сознания), danger (поведение, опасное для себя или других). Добавляй пункт, только если он прямо описан в тексте. Не делай выводов о состоянии или диагнозе ребёнка. Определи, с чем семье нужна помощь в первую очередь, только если это прямо сказано, иначе null. Верни только JSON по схеме.
```

**Вызов 3. Объяснение шага.**

Вход: `service_id`, название, ведомство, возрастная группа, язык, список документов, флаги `needs_clarification` и `deadline_compressed`. Схема: `{ "explanation": string, maxLength 400 }`.

```
Ты пишешь объяснение одного шага маршрута для родителя простым языком на языке {lang}. Два или три предложения, обращение на «вы». Объясни, зачем нужен этот шаг и что семья получит на выходе. Если deadline_compressed, спокойно объясни, что шаг стоит сделать раньше обычного, потому что скоро истекает действующий документ. Никогда не утверждай ничего о здоровье или развитии ребёнка, не называй диагнозы и состояния, не упоминай лекарства, дозировки и лечение, не делай прогнозов. Для услуг MED_MSE_REFERRAL и SOC_MSE обязательно скажи, что вопрос об инвалидности решается вместе с врачом. Верни только JSON по схеме.
```

**Вызов 4. Разбор документа.**

Вход: первые 4000 символов извлечённого текста после маскирования. Схема: `{ "doc_type": enum из document_types без medical_card_052, "issued_at": date|null, "valid_until": date|null, "issuer": string|null }`.

```
Ты определяешь тип официального документа и достаёшь из него только реквизиты: тип из закрытого списка, дату выдачи, дату окончания действия, кем выдан. Если реквизита нет в тексте, верни null. Не пересказывай и не извлекай медицинское содержание документа. Верни только JSON по схеме.
```

### 12.3. Фильтр формулировок

Файл `data/filter_patterns.json`: списки регулярных выражений по языкам и категориям, плюс `allowlist` (названия услуг из справочника, в том числе «центр поддержки детей с РАС»). Текст сначала очищается от фраз из `allowlist`, затем проверяется.

Стартовый набор (расширь и отметь `needs_review` для казахского):

| Категория | ru | kk |
| --- | --- | --- |
| Утверждение о ребёнке | `у (вашего \|этого )?ребёнка (есть\|выявлен\|диагностирован)`, `(ваш )?ребёнок (болен\|страдает)` | `балаңыз(да)? .* (бар\|ауырады)` |
| Диагнозы | `диагноз`, `аутизм`, `\bРАС\b` вне allowlist | `диагноз`, `аутизм` |
| Лечение и препараты | `лечени`, `препарат`, `таблетк`, `\b\d+\s?(мг\|мл)\b` | `емдеу`, `дәрі` |
| Прогнозы | `не сможет`, `никогда не`, `на всю жизнь` | `ешқашан` |

Срабатывание: повторная генерация с текстом нарушения в промпте. После второго срабатывания используется `explanation_template` из справочника. Каждое срабатывание пишется в лог `filter_events`, его показывает демо (раздел 19.4).

## 16. PWA

### 16.1. Манифест (`app/manifest.ts`)

- `name`: «AqylRoute», `short_name`: «AqylRoute», `description` на русском.
- `start_url`: `/?source=pwa`, `scope`: `/`, `display`: `standalone`, `orientation`: `any`, `lang`: `ru`.
- `background_color` и `theme_color` из тёмной темы.
- Иконки 192 и 512 пикселей плюс отдельная `maskable` 512, сгенерированные из своего геометрического SVG-логотипа, и `apple-touch-icon` 180.
- `shortcuts`: «Мой план» (`/ru/plan`), «Документы» (`/ru/documents`).

### 16.2. Service worker (Serwist)

- Precache: собранные ассеты и страница `/offline`.
- Статика (`/_next/static`, шрифты, иконки): `CacheFirst`.
- Навигация по страницам: `NetworkFirst` с таймаутом 3 секунды, при неудаче `/offline`.
- `GET /api/plans/*`, `GET /api/documents`, `GET /api/notifications`: `NetworkFirst`, кеш `api-private`, срок 7 дней.
- Остальные `GET /api/*`: `NetworkOnly`.
- Все `POST`, `PATCH`, `DELETE`: `NetworkOnly`, без фоновой синхронизации.
- Файлы документов и PDF: `NetworkOnly`, API отдаёт их с `Cache-Control: no-store`.

### 16.3. Офлайн

- Родитель без сети открывает свой последний план, шаги и список документов. Сверху баннер «Нет сети. Показаны данные от {дата и время}».
- Кнопки, меняющие данные, неактивны с подсказкой «Нужен интернет».
- Интервью без сети не начинается, показывается понятное сообщение.
- Кабинет куратора офлайн не поддерживается, показывается `/offline`.

### 16.4. Установка и обновление

- Своя кнопка «Установить приложение» в меню, обработка `beforeinstallprompt`. На iOS вместо неё инструкция: «Поделиться», затем «На экран Домой».
- Во время интервью предложение установки не показывается.
- Когда новый service worker ждёт активации, показывать «Доступно обновление» с кнопкой перезагрузки.

### 16.5. Безопасность

- При выходе из аккаунта web отправляет service worker сообщение, и он удаляет кеш `api-private`.
- Ответы с `Cache-Control: no-store` никогда не кешируются.
- Web push в MVP не делается.

### 16.6. Проверки

1. Chrome DevTools, вкладка Application: манифест без ошибок, приложение устанавливаемое, service worker активен.
2. Установленное приложение открывается в отдельном окне без адресной строки на Android и десктопе, на iOS добавляется на экран «Домой».
3. Родитель входит, открывает план, выключает сеть и перезагружает: план открывается с баннером.
4. После выхода в Cache Storage нет `api-private`.
5. Выпуск новой сборки показывает «Доступно обновление».

## 19. Синтетические кейсы, тесты и демо

Кейсы лежат в `data/fixtures/` и служат одновременно демо-данными и эталоном для автотестов. Дата расчёта для обоих `2026-10-01`. Тест движка строит план из `profile_expected`, без LLM. Отдельный интеграционный тест проходит интервью с LLM в режиме заглушки, отвечая на каждый заданный вопрос из словаря `answers` фикстуры, и проверяет, что вопросов от 8 до 12, все они были допустимы в момент показа и все шесть обязательных заданы. Порядок и состав необязательных вопросов у заглушки и у реальной модели может отличаться от `answers`, поэтому словарь `answers` в фикстуре содержит ответы на все вопросы, которые могут стать допустимыми, а `profile_expected` описывает профиль для теста движка.
