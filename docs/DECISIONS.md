# Решения вне спецификации

Формат: `YYYY-MM-DD — решение — причина.`

- 2026-09-30 — репозиторий не переименован в `aqylroute/`, структура из раздела 2 (`docs/`, `data/`, `apps/`) создаётся прямо в корне текущего репозитория (`medhub`), без обёртывающей директории — обёртка в разделе 2 обозначала имя проекта, а не обязательную вложенность.
- 2026-09-30 — исходный `CLAUDE.md` (React/Vite/shadcn стартер) заменён по явному правилу раздела 0 на одну строку, указывающую на `docs/SPEC.md`. Правила фронтенд-стартера (shadcn/react-bits и т.д.) не переносились, так как раздел 2 спецификации задаёт свой стек (Next.js) для `apps/web`.
- 2026-09-30 — вопросы `Q07`, `Q11` (`date_or_unknown`) моделируются в `questions.json` как `options: [{code: "unknown", ...}]` плюс `answer_type: "date_or_unknown"`, обозначающий, что помимо кода `unknown` допустимо значение в формате даты `YYYY-MM-DD`. Явного формата в разделе 5 не задано.
- 2026-09-30 — `show_if` вопросов Q17 и Q18 записан как литеральная строка `"filler"` (а не JSON-объект условия), как буквально описано в разделе 5.2 таблице и абзаце после неё.
- 2026-09-30 — поле `age_window.max_age` для `EDU_EARLY_HELP` заполнено значением-заглушкой `3` с пометкой `TODO(mentor)` внутри `data/services.json`; точная граница не определена спецификацией (раздел 9.3). Также добавлена строка в `docs/OPEN_QUESTIONS.md`.
- 2026-09-30 — для валидации `profile_field` вопросов (раздел 10.1) список допустимых путей профиля захардкожен в `apps/api/tests/test_data.py`, отдельная JSON Schema для профиля не создавалась, так как раздел 3 (этап 0) перечисляет только `questions.json`, `services.json`, `document_types.json`, `providers.json`, `sources.json` как файлы, требующие схем.
- 2026-09-30 — версии `CasePlan` (раздел 11.3: "Запиши это решение в docs/DECISIONS.md"): новая версия создаётся только при (1) построении черновика движком, (2) добавлении/удалении шага куратором, (3) подтверждении куратором. Переходы статуса шага (раздел 11.4), перенос срока с причиной и переосчёт сроков планировщиком (этап 2) меняют текущую версию на месте и пишутся в `status_history` шага. Причина: раздел 11.3 явно требует версионирование только для этих трёх событий и явно говорит, что переосчёт планировщика — "на месте"; версионирование по каждому клику статуса привело бы к неконтролируемому росту числа версий без пользы для истории "движок против куратора" (экран "История", раздел 15.2).
- 2026-09-30 — модуль `apps/api/app/modules/llm/` в этапе 1 реализован только в режиме заглушки (вызовы 1-3: выбор вопроса, разбор Q17, объяснение шага из `explanation_template_*`). Реальная интеграция с OpenAI structured outputs, вызов 4 (разбор документа) и фильтр формулировок (раздел 12.3, `data/filter_patterns.json`) — предмет этапа 2 ("LLM-модуль (раздел 12)" явно перечислен в проверках этапа 2, а не этапа 1). При непустом `OPENAI_API_KEY` клиент сейчас намеренно бросает `LlmNotConfiguredError`, а не молча использует заглушку, чтобы это не осталось незамеченным при переходе к этапу 2.
- 2026-09-30 — маскирование адресов (раздел 12.1) реализовано эвристическим regex (ключевые слова мкр/ул/дом/кв + номер), а не полноценным NER — в стеке проекта нет библиотеки распознавания адресов. Может пропускать нестандартные форматы адреса; это допустимо, так как маскирование — дополнительный барьер, а ФИО/адрес в вопросы интервью и так не запрашиваются (раздел 5.4).
- 2026-09-30 — `POST /interview/{family}/clarify` создаёт запись `Clarification`, но ответная часть сценария "родитель отвечает на уточнение -> профиль обновляется -> строится новая версия черновика" не реализована в этапе 1: она требует пересборки плана и пересечения с уведомлениями (раздел 18, этап 2). Строка добавлена в `docs/OPEN_QUESTIONS.md`.
